# ADR 0014：账户级有界 IMAP 会话协调

状态：已接受

日期：2026-07-26

## 背景

阶段十五的完整同步会为单个账户同时建立三条 IMAP worker 会话。用户在同步期间打开尚无正文的邮件时，按需正文路径还会建立第四条会话。`MailRuntime` 的两个全局网络许可只计算高层操作，不知道一个 Provider 操作内部会创建多少协议会话。

应用没有取消同步任务，也没有让正文请求复用同步中的 `Session`。但部分服务端或中间网络设备会在同一账户达到并发连接限制时重置已有连接，因此用户看到的结果是正文开始下载后完整同步以 `ConnectionReset` 失败。

直接共享长期存活的 `async-imap::Session` 会把选中邮箱状态、故障连接、读写超时和第三方类型带到运行时层；为此建立跨层通用连接池会改变既有 port 与 Adapter 边界，也会让账户重认证和 Supervisor generation 的生命周期更复杂。

## 决策

- `ImapSyncProvider` port、DTO 和 `state.rs` 注入方式保持不变；会话协调只存在于具体 `AsyncImapProvider` 内。
- 每个公开 `account_id` 共享一个最多三条主动会话的异步预算。
- 完整同步只租用两条 worker 会话，并把待抓 UID 划为两个互不重叠的集合；第三条容量始终可供正文、附件、持久化待办、Drafts 或 Sent 操作使用。
- 账户启用“收取邮件全文”时，邮件头阶段完成后继续复用这两条同步会话补齐本地缺失正文，不为全文阶段额外租用会话；单文件夹 Drafts 定向刷新不执行该补齐。
- 每个操作取得预算后按需连接，操作完成后 LOGOUT/关闭；失败连接不复用。这里的“池”是有界会话容量与按需扩缩，不是长期缓存已登录的协议对象。
- 第四个并发会话请求等待预算，不新建连接，也不取消或抢占已经运行的同步。
- 预算注册表只保存 `Semaphore` 弱引用；没有活跃租约时账户条目可自然回收，不增加清理 Worker。
- 普通连接继续使用 TCP 30 秒、每次读写 60 秒的超时。未来若实现 IMAP IDLE，必须单独设计静默等待超时与重连状态机，不能直接复用当前连接行为。

## 影响

- 完整同步的同账户抓取并发从三降为二，极大文件夹的峰值吞吐可能略降，但避免正文请求把连接数推到四并触发服务端重置。
- 同步（包括可选全文阶段）、按需正文和一个额外操作同时发生时仍受总预算约束；超过三个的操作会等待而不是制造连接风暴。
- `core`、application、Command、Repository、数据库和前端事件契约均不改变；第三方 IMAP 类型仍只位于 protocol Adapter。
- 这不是通用连接复用池。连接建立成本仍按操作承担，换取故障隔离、配置更新清晰和操作结束后的确定关闭。

## 验证门禁

- 单元测试固定每账户上限为三、同步 worker 数为二。
- 同步持有两条租约时，交互请求可以取得第三条；第四条在已有租约释放前必须等待。
- 同一账户复用活跃预算，不同账户使用独立预算。
- Windows 实机在完整同步期间连续打开缺少正文的邮件，同步与正文都应继续完成，日志中不得再出现由第四条连接触发的同步重置。
